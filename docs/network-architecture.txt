В плане описан кластер из 4 узлов, а не 3:
- Master — это ноутбук (192.168.1.5), координатор всего кластера.
- 3 «собранных ПК» — это как раз worker-узлы (192.168.1.10–12), которые делают основную работу.

То есть ваши 3 ПК — это воркеры, а ноутбук выступает мастером. Ниже расскажу и про то, как 3 ПК общаются между собой, и про роль мастера — без неё картина неполная.

---

Физическая топология

                    ИНТЕРНЕТ
                        │
                ┌───────┴──────────┐
                │  Домашний роутер │  192.168.1.1  (шлюз + DHCP + встроенный свитч)
                └─┬────┬────┬────┬─┘
       Ethernet   │    │    │    │   Ethernet (витая пара, лучше Gigabit)
          ┌───────┘    │    │    └────────────┐
          │       ┌────┘    └────┐            │
     ┌────┴────┐ ┌┴────────┐ ┌───┴─────┐ ┌────┴────┐
     │ Ноутбук │ │  ПК #1  │ │  ПК #2  │ │  ПК #3  │                                                                                                       
     │ MASTER  │ │ worker1 │ │ worker2 │ │ worker3 │
     │ .1.5    │ │ .1.10   │ │ .1.11   │ │ .1.12   │                                                                                                       
     └─────────┘ └─────────┘ └─────────┘ └─────────┘
        Ubuntu Server 22.04 на всех узлах, подсеть 192.168.1.0/24                                                                                     
Ключевая идея уровня «железа»: роутер для домашней сети — это не только маршрутизатор в интернет, но и свитч. Все LAN-порты роутера находятся в одном сегменте (один broadcast-домен, одна подсеть 192.168.1.0/24).

Из этого следует главное:

- Когда ПК #1 хочет отправить данные ПК #2, трафик не идёт «навуется — он коммутируется напрямую внутри свитча роутера наскорости порта (в идеале 1 Гбит/с). Это критично для Hadoop/Spark, где узлы гоняют между собой огромный объём данных (репликация HDFS, shuffle Spark).
- Узлы находят друг друга по MAC-адресам через ARP: «кто такой → дальше кадры летят напрямую. Шлюз (192.168.1.1) нужен воркерамтолько для выхода в интернет (обновления apt, скачивание пакетов), а не для общения между собой.

Теперь по пунктам плана.

---

1.1 — Статические IP: почему и как

Зачем. По умолчанию роутер раздаёт адреса по DHCP, и они могут меняться после перезагрузки. Для кластера это смерть: NameNode запоминает воркеров по
адресам/именам, и если у ПК #2 адрес «уехал», мастер его потеряя.

На Ubuntu Server 22.04 сеть настраивается через netplan (рендерanager на сервере обычно нет). На каждом ПК правится файл вида/etc/netplan/00-installer-config.yaml:

network:
  version: 2
  ethernets:
    enp3s0:                      # реальное имя интерфейса смот
      dhcp4: no
      addresses: [192.168.1.10/24]   # у worker2 → .11, у worke
      routes:
        - to: default
          via: 192.168.1.1          # шлюз = роутер, только для интернета
      nameservers:
        addresses: [192.168.1.1, 8.8.8.8]

Потом sudo netplan apply.

Два подводных камня, которых нет в документе:
1. Подсеть должна совпадать с роутером. Если ваш роутер по умол 192.168.100.x, то адреса 192.168.1.x из плана работать не будут— либо поменяйте план под свою подсеть, либо перенастройте LAN роутера на 192.168.1.0/24.
2. Конфликт с DHCP-пулом. Статические адреса .5, .10, .11, .12 торый роутер раздаёт по DHCP (либо сделайте на роутереDHCP-reservation по MAC). Иначе роутер может выдать .10 вашему телефону, и будет конфликт адресов.

1.2 — /etc/hosts: имена вместо цифр

Дома нет своего DNS-сервера, поэтому имена zeer-master, zeer-worker1 и т.д. ниоткуда не «резолвятся». Файл /etc/hosts — это локальная таблица «имя → IP», и
она должна быть идентичной на всех 4 узлах:

192.168.1.5   zeer-master
192.168.1.10  zeer-worker1
192.168.1.11  zeer-worker2
192.168.1.12  zeer-worker3

Почему это не косметика, а требование Hadoop: весь Hadoop-стек (HDFS, YARN, ZooKeeper, Kafka) адресует узлы по хостнеймам, а не по IP, и требует, чтобы
прямое и обратное разрешение имён было согласованным на всех узрегистрируется на NameNode, ZooKeeper не соберёт кворум и т.п.

Классический баг Ubuntu, о котором план молчит: в /etc/hosts по
127.0.1.1   <имя-хоста>
Из-за неё Hadoop-демон привязывается к loopback 127.0.1.1 и слуы до него достучаться не могут. На узлах кластера эту строкунужно убрать/закомментировать, чтобы имя резолвилось в реальный LAN-адрес.

1.3 — SSH без пароля: как мастер «дирижирует» воркерами

Зачем это нужно. Hadoop запускается не вручную на каждой машине, а централизованно: скрипты start-dfs.sh / start-yarn.sh на мастере по очереди заходят по SSH
на воркеры и стартуют там демоны (DataNode, NodeManager…). Если пароль, автоматизация была бы невозможна.

Механика (направление важно — мастер → воркеры):
1. На узлах генерируется пара ключей: ssh-keygen -t rsa создаёт приватный ~/.ssh/id_rsa (секрет, остаётся на месте) и публичный ~/.ssh/id_rsa.pub.
2. ssh-copy-id hadoop@zeer-worker1 кладёт публичный ключ мастерys на воркере.
3. Теперь при подключении воркер проверяет, что у пришедшего есть приватный ключ, парный к сохранённому публичному — пароль не нужен.

Обратите внимание: в плане ssh-copy-id делается и на zeer-master (сам на себя) — это тоже нужно, потому что мастер часто запускает демоны и локально через
тот же механизм SSH. Проверка ssh zeer-worker1 hostname должна са пароля — это критерий, что всё готово.

Важный нюанс: все команды делаются под пользователем hadoop (соспарольный вход — всё привязано именно к этому пользователю, а не к root.

Как эти 3 ПК реально «разговаривают» в работе

Пункты 1.1–1.3 создают фундамент (адреса, имена, доверенный доступ). А вот что поверх него происходит, когда кластер запущен, — здесь и виден смысл
«взаимодействия 3 ПК»:

┌────────────┬──────────────────────────────────────────────────────────────┬──────────────────────────────────────────────┐
│   Сервис   │                             Общение между 3 ПК (peer-to-peer)                             │              Общение с мастером              │
├────────────┼──────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
│ HDFS       │ DataNode'ы гоняют между собой копии блоков: dfs.replication=2 → каждый блок лежит на 2 из │ Каждый DataNode шлёт heartbeat + отчёт о     │
│            │  3 ПК. При записи данные идут по цепочке ПК→ПК.              │ блоках на NameNode (ноутбук).                │
├────────────┼───────────────────────────────────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
│ ZooKeeper  │ 3 ПК образуют кворум: выбирают 1 лидера и 2 фоллуются (порты │ —                                            │
│            │  2888/3888). Именно поэтому ZK ставят в нечётном числе — 3.                               │                                              │
├────────────┼──────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
│ Kafka      │ 3 брокера реплицируют партиции между собой (replication.factor=3).                        │ Координацию берёт ZooKeeper на этих же ПК.   │
├────────────┼──────────────────────────────────────────────────────────────┼──────────────────────────────────────────────┤
│ YARN /     │ NodeManager'ы запускают контейнеры; при Spark-джобе экзекьюторы на разных ПК обмениваются │ ResourceManager (ноутбук) раздаёт задачи и   │
│ Spark      │  данными (shuffle) напрямую ПК↔ПК.                           │ следит за ресурсами.                         │
└────────────┴───────────────────────────────────────────────────────────────────────────────────────────┴──────────────────────────────────────────────┘

То есть между собой 3 ПК общаются как равные (репликация HDFS, кворум ZooKeeper, репликация Kafka, shuffle Spark), а мастер выступает координатором —
принимает heartbeat'ы, назначает задачи, хранит метаданные. И вчерез свитч роутера в пределах одной подсети, что вы и заложилипунктами 1.1–1.3.
